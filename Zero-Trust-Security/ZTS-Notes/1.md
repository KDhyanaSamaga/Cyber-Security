Think of **Zero Trust** as a security philosophy built around one simple change:

> **Before Zero Trust:** “You are inside the network, so you are probably trusted.”
> **With Zero Trust:** “Being inside the network proves nothing. Verify every access request.”

This concept became important because the traditional network security model started breaking down as organizations moved to cloud, remote work, mobile devices, SaaS, and distributed applications.

---

# 1. What is Zero Trust?

**Zero Trust Architecture (ZTA)** is a security model where **no user, device, application, or network location is automatically trusted**.

Every access request should be evaluated based on things such as:

* Who is the user?
* Is the user authenticated?
* What device are they using?
* Is the device healthy/compliant?
* What resource are they trying to access?
* What permissions do they have?
* Where is the request coming from?
* What is the context of the request?
* Is the behavior suspicious?

The basic idea is:

```text
          ACCESS REQUEST
                |
                v
       +-------------------+
       | Verify identity   |
       +-------------------+
                |
                v
       +-------------------+
       | Verify device     |
       +-------------------+
                |
                v
       +-------------------+
       | Check permissions |
       +-------------------+
                |
                v
       +-------------------+
       | Check context     |
       +-------------------+
                |
                v
          Allow / Deny
```

And importantly:

**Authentication ≠ automatic authorization.**

Even if you successfully log in, Zero Trust can still deny access to a particular resource.

---

# 2. Why was Zero Trust introduced?

To understand this, first understand the **old security model**.

Traditionally, organizations designed their networks something like this:

```text
                    INTERNET
                       |
                 [Firewall]
                       |
              -----------------
              |               |
           Internal        Internal
           Network         Network
              |
       ----------------
       |       |      |
      PC      PC     Server
```

The firewall was treated as the major security boundary.

The assumption was roughly:

```text
Outside network → UNTRUSTED ❌

Inside network  → TRUSTED ✅
```

This is often called the **castle-and-moat model**.

Imagine a castle:

```text
                 INTERNET
                    |
             🚫 WALL / FIREWALL
                    |
                    v
             +-------------+
             |   CASTLE    |
             |             |
             |   Servers   |
             |   PCs       |
             |   Database  |
             +-------------+
```

The organization concentrated security around the perimeter.

Once someone got through the perimeter:

```text
                    Firewall
                       |
                       v
                +-------------+
                | Internal    |
                | Network     |
                |             |
                | User A --->  |
                | Server       |
                | Database     |
                +-------------+
```

There could be **too much implicit trust inside the network**.

# 3. What problems existed before Zero Trust?

There were several major problems.

## Problem 1: "Inside = Trusted"

Suppose an attacker compromises one employee's laptop.

Traditional model:

```text
Attacker
   |
   | stolen credentials
   v
Employee Laptop
   |
   v
Internal Network
   |
   +---- Server A
   |
   +---- Server B
   |
   +---- Database
```

Once the attacker entered the internal network, they could potentially move toward other systems.

This is called:

### **Lateral Movement**

For example:

```text
Compromised PC
      ↓
File Server
      ↓
Application Server
      ↓
Database
      ↓
Domain Controller
```

The attacker keeps moving deeper into the organization.

Zero Trust tries to reduce this by enforcing access controls **between resources**, not just at the network perimeter.

---

# 4. Problem: Remote employees

The traditional model assumed:

```text
Employee
   ↓
Office
   ↓
Corporate Network
```

But modern organizations look more like:

```text
                 Cloud
                   |
Employee ---- Internet ---- SaaS
                   |
Laptop -----------+
                   |
Mobile -----------+
                   |
Home network -----+
```

Employees might work from:

* Home
* Coffee shops
* Airports
* Different countries
* Personal networks
* Corporate offices

So the question becomes:

> **What exactly does "inside the network" mean anymore?**

There may not be a single corporate network.

---

# 5. Problem: Cloud computing

Earlier:

```text
Company
   |
   +--- Data Center
          |
          +--- Servers
          +--- Database
          +--- Applications
```

Now:

```text
Company
   |
   +--- AWS
   +--- Azure
   +--- Google Cloud
   +--- SaaS
   +--- On-premise
   +--- Employee devices
```

Resources are distributed everywhere.

Therefore, simply protecting the corporate network perimeter isn't sufficient.

You need to protect the **resource itself**.

---

# 6. Problem: Stolen credentials

Suppose an attacker obtains:

```text
Username: dhyana
Password: ********
```

Traditional system might see:

```text
Correct username + password
          ↓
       LOGIN ✅
          ↓
     Access granted
```

Zero Trust asks additional questions:

```text
Correct credentials?
       ↓
      YES
       ↓
Is device trusted?
       ↓
Is device compliant?
       ↓
Is this user allowed to access this resource?
       ↓
Is this request unusual?
       ↓
Allow / Deny
```

So:

**Valid credentials do not automatically mean valid access.**

---

# 7. Problem: Excessive privileges

Imagine an employee only needs:

```text
Employee → Application A
```

But their account has:

```text
Employee
   |
   +--> Application A
   +--> Application B
   +--> Database
   +--> File Server
   +--> Admin Panel
```

That's dangerous.

If their account is compromised, the attacker inherits those permissions.

Zero Trust strongly emphasizes:

### **Least Privilege**

Give users/applications only the access they actually need.

For example:

```text
Developer
   |
   +--> Development Server ✅
   |
   +--> Production Database ❌
   |
   +--> HR Database ❌
```

---

# 8. Problem: Insider threats

The attacker doesn't necessarily have to be an outsider.

Consider:

```text
Employee
   ↓
Already inside organization
   ↓
Accesses sensitive database
```

Traditional perimeter security may not be very effective here because the person is already inside.

Zero Trust doesn't automatically trust someone merely because:

* they are an employee,
* they are connected to the company network,
* they previously authenticated.

Access continues to be controlled based on identity, permissions, context, and resource.

---

# 9. Problem: IoT and many different devices

Modern organizations have:

```text
Laptops
Phones
Servers
IoT
Cameras
Cloud workloads
Containers
Virtual machines
APIs
Microservices
```

You can't simply say:

> "Everything connected to our network is trusted."

A compromised IoT device could potentially become an entry point.

Zero Trust therefore considers **devices and workloads as security subjects**, not just human users.

---

# 10. What existed before Zero Trust?

It's important to understand this correctly.

Zero Trust did **not** mean that organizations had no security before it.

They already had:

* Firewalls
* VPNs
* IDS/IPS
* Antivirus
* Network segmentation
* Access control lists
* Authentication
* Encryption
* SIEM
* Proxy servers

The problem was that these controls were often organized around a **perimeter-centric security model**.

Zero Trust changes the security philosophy.

Instead of:

```text
           TRUST
             ↓
       Internal Network
       /       |       \
    Server   Database   App
```

the approach becomes:

```text
User ──→ Verify ──→ Resource
Device ─→ Verify ──→ Resource
App ───→ Verify ──→ Resource
```

# 11. The core idea

You will often hear:

## **"Never trust, always verify."**

But don't interpret that literally as:

> "Never trust anyone."

It means:

> **Don't grant implicit trust based merely on network location or previous access. Continuously evaluate whether access should be allowed.**

A simplified Zero Trust access decision is:

```text
                ACCESS REQUEST
                      |
                      v
             +----------------+
             | Who are you?   |
             +----------------+
                      |
                      v
             +----------------+
             | What device?   |
             +----------------+
                      |
                      v
             +----------------+
             | What resource? |
             +----------------+
                      |
                      v
             +----------------+
             | What privilege?|
             +----------------+
                      |
                      v
             +----------------+
             | Context/risk?  |
             +----------------+
                      |
                      v
                ALLOW / DENY
```

# 12. What is the scope of Zero Trust?

This is very important for your **Zero Trust Security** subject.

Zero Trust isn't just about users.

Its scope includes several areas:

### 1. Users

```text
Employee
Admin
Contractor
Customer
Service account
```

Verify their identity and permissions.

---

### 2. Devices

```text
Laptop
Mobile
Server
IoT
Virtual machine
```

Check things like device identity and security posture.

---

### 3. Applications

Applications should not automatically trust each other.

For example:

```text
Frontend
   ↓
API
   ↓
Database
```

The API should authenticate/authorize requests rather than assuming the frontend is trustworthy.

---

### 4. Data

Protect the actual data:

```text
Public data
Internal data
Confidential data
Sensitive data
```

Access should depend on who/what is requesting it.

---

### 5. Networks

Zero Trust reduces dependence on:

```text
"You're on our internal network, therefore you're trusted."
```

Network segmentation and microsegmentation can restrict communication.

---

### 6. Workloads

Modern systems contain:

```text
Containers
Microservices
VMs
Cloud workloads
Serverless functions
```

These also need identity and authorization.

---

# 13. Zero Trust in a modern company

Imagine this architecture:

```text
                   INTERNET
                       |
             +------------------+
             | Identity / Auth  |
             +------------------+
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
     Employee        Device        Application
        |              |              |
        +--------------+--------------+
                       |
                 Policy Decision
                       |
              +--------+--------+
              |                 |
              v                 v
          ALLOW             DENY
              |
              v
        Specific Resource
              |
       +------+------+------+
       |      |      |      |
      API    DB    Server  Cloud
```

The key idea is that **access is decided around the resource**, rather than simply based on whether the requester is inside the corporate network.

The environment has changed.

### Old environment

```text
Employees
    ↓
Office
    ↓
Corporate Network
    ↓
Corporate Servers
```

### Modern environment

```text
              Cloud
                |
```

You can remember it like this for your exam:

### Traditional security

```text
Protect the NETWORK
        ↓
Trust inside
        ↓
Control outside
```

### Zero Trust

```text
Protect RESOURCES
        ↓
Verify every access request
        ↓

        ↓
Continuously monitor
```

# 16. One simple real-world example

Imagine your college network.

Traditional thinking:

```text
Student connects to college Wi-Fi
             ↓
       Internal Network
             ↓
       Access systems
```

But suppose someone steals a student's laptop credentials.

They connect to the network.

Traditional perimeter-based thinking might give them too much access once they're inside.

Zero Trust would instead evaluate:

```text
Who?
 ↓
Student account

Device?
 ↓
Is the device known/compliant?

Resource?
 ↓
College database

Permission?
 ↓
Student doesn't have database access

Decision
 ↓
DENY ❌
```

Even though:

```text
Student account = valid
Network connection = valid
```

the request can still be denied.

```text
        ZERO TRUST
            ↓
   "Never trust implicitly"
```

### One-line exam definition

> **Zero Trust is a security model that assumes no user, device, application, or network is inherently trusted and requires continuous verification and authorization before granting access to resources.**

And the **reason it was introduced** is not that traditional security was useless; rather, **the traditional perimeter-based assumption of "trust the internal network" became inadequate for cloud computing, remote work, mobile/IoT devices, distributed applications, stolen credentials, and modern cyber threats.**
